# v0.1.0 — Project Foundation (Learning Document)

---

## 1. The Big Picture

### What is v0.1.0?

v0.1.0 is the "Project Foundation" milestone. It sets up everything needed before we write any business logic (properties, bookings, payments, etc.). Think of it as building the house's foundation, plumbing, and electrical wiring before putting up walls and furniture.

After v0.1.0, we have:
- A Laravel API backend that can receive HTTP requests and return JSON
- A React frontend that can display pages and talk to the API
- A PostgreSQL database ready to store data
- A Redis server ready to handle background jobs and caching
- A Mailpit server that catches emails locally for testing
- A GitHub Actions CI pipeline that automatically tests our code on every pull request
- A branch protection rule that prevents broken code from reaching `main`

### Why do foundation work before business features?

If you try to build features (like "create a booking") without a working foundation, you'll constantly fight environment issues, broken builds, and configuration problems. By getting the foundation right first:

- Every developer (or just you) can run the full app with one command (`docker compose up -d`)
- Tests run automatically on every PR, catching bugs before they reach `main`
- The folder structure is clear, so you know where to put new code
- You don't need to install PHP, Node, PostgreSQL, or Redis on your laptop

### How the pieces fit together

```
You (browser)
    │
    ▼
Frontend (React SPA at localhost:5173)
    │ HTTP requests to /api/v1/...
    ▼
Backend API (Laravel at localhost:8000)
    │
    ├──▶ PostgreSQL (stores all data)
    ├──▶ Redis (queues background jobs, caches data)
    └──▶ Mailpit (catches outgoing emails)

Queue Worker (same Laravel code, processes background jobs from Redis)
```

The frontend is what the user sees. It sends requests to the backend. The backend processes those requests, reads/writes data in PostgreSQL, and sometimes queues background jobs in Redis. The queue worker picks up those jobs and processes them. Mailpit catches any emails the backend sends so you can inspect them without a real email server.

## 2. Docker Concepts for Beginners

### What is Docker?

Docker lets you run applications in isolated environments called "containers." Each container has its own operating system, libraries, and tools — completely separate from your Windows laptop.

**Analogy:** Think of containers as shipping containers on a cargo ship. Each one is self-contained with everything it needs inside. It doesn't matter what ship (computer) carries it — the contents work the same everywhere.

### What is an image?

An image is a blueprint for creating a container. It's like a recipe that says "start with PHP 8.3, add these extensions, install Composer." You build an image once, then create containers from it.

Our project has two custom images:
- `docker/backend/Dockerfile` → builds the PHP image for Laravel
- `docker/frontend/Dockerfile` → builds the Node image for React/Vite

### What is a container?

A container is a running instance of an image. When you run `docker compose up -d`, Docker creates containers from images and starts them. Each container is like a tiny virtual computer running one service.

### What is Docker Compose?

Docker Compose is a tool for running multiple containers together. Instead of starting 6 containers manually with 6 separate commands, you define them all in `docker-compose.yml` and start them with one command.

### Why Docker instead of installing everything locally?

Without Docker, you'd need to install on your Windows laptop:
- PHP 8.3 with specific extensions (pdo_pgsql, redis, intl, etc.)
- Composer (PHP package manager)
- Node.js 20
- npm (Node package manager)
- PostgreSQL 16
- Redis 7

Each of these can have version conflicts, PATH issues, and Windows-specific problems. With Docker, you just need Docker Desktop installed — everything else runs inside containers.

### Docker Compose commands explained

| Command | What it does |
|---------|-------------|
| `docker compose up -d` | Start all services in the background. `-d` means "detached" (don't block your terminal). |
| `docker compose run --rm api <command>` | Start a temporary container from the `api` service, run a command, then delete the container. `--rm` means "remove after done." |
| `docker compose run --rm --no-deps frontend <command>` | Same as above but `--no-deps` means "don't start dependent services" (useful when you only need Node, not the whole stack). |
| `docker compose exec api <command>` | Run a command inside an already-running container. Unlike `run`, this doesn't create a new container. |
| `docker compose build` | Rebuild images from Dockerfiles. Needed after you change a Dockerfile. |
| `docker compose down` | Stop and remove all containers. Data in volumes (like the database) is preserved. |
| `docker compose down -v` | Stop, remove containers, AND delete volumes. This resets the database completely. |
| `docker compose ps` | Show the status of all containers (running, healthy, exited). |
| `docker compose logs <service>` | Show the output/logs from a specific service. |

## 3. Each Docker Service Explained

### frontend

**What it does:** Runs the Vite development server, which serves the React application and provides hot-reload (changes appear instantly in the browser without refreshing).

**Why LodgeFlow needs it:** The owner interacts with LodgeFlow through a web browser. The frontend is the user interface — forms, buttons, navigation, dashboard cards.

**Port:** localhost:5173

**How to check:** Open http://localhost:5173 in your browser. You should see the LodgeFlow app shell.

### api

**What it does:** Runs the Laravel application using PHP's built-in development server. It receives HTTP requests from the frontend (like "create a property" or "list bookings") and returns JSON responses.

**Why LodgeFlow needs it:** The backend enforces business rules (e.g., "you can't book a unit that's already booked"), validates data, and manages the database.

**Port:** localhost:8000

**How to check:** Run `curl.exe -s http://localhost:8000/api/v1/health` — should return `{"status":"ok"}`.

### queue-worker

**What it does:** Runs the same Laravel code as `api`, but instead of listening for HTTP requests, it listens for background jobs in Redis. When a job appears (like "create a cleaning task after checkout"), it processes it.

**Why LodgeFlow needs it:** Some operations shouldn't block the user. When an owner checks out a guest, the API responds immediately ("checkout successful") and queues a background job to create the cleaning task. The queue worker handles that job separately.

**Port:** None (it doesn't accept HTTP requests).

**How to check:** Run `docker exec lodgeflow-queue-worker-1 php artisan queue:monitor redis:default,redis:cleaning-tasks` — should show both queues as "OK".

### db

**What it does:** Runs PostgreSQL 16, the relational database that stores all LodgeFlow data (properties, units, guests, bookings, payments, etc.).

**Why LodgeFlow needs it:** Every piece of data in the application lives in PostgreSQL. It enforces data integrity (foreign keys, unique constraints, check constraints).

**Port:** localhost:5432

**How to check:** Run `docker exec lodgeflow-db-1 pg_isready -U lodgeflow` — should say "accepting connections".

### redis

**What it does:** Runs Redis 7, an in-memory data store used for two purposes: (1) as a queue broker for background jobs, and (2) as a cache for frequently-accessed data.

**Why LodgeFlow needs it:** The queue worker needs somewhere to find pending jobs. Redis is fast and lightweight for this. It also speeds up the app by caching things like dashboard calculations.

**Port:** localhost:6379

**How to check:** The `docker compose ps` output shows "healthy" next to the redis container.

### mailpit

**What it does:** Runs a fake email server. Any email the Laravel backend sends (via SMTP on port 1025) gets caught by Mailpit instead of being delivered to a real inbox. You can view caught emails in the Mailpit web UI.

**Why LodgeFlow needs it:** During development, you might send emails (password resets, notifications). Mailpit lets you see those emails without configuring a real email service.

**Ports:** localhost:8025 (web UI), localhost:1025 (SMTP)

**How to check:** Open http://localhost:8025 in your browser. You should see the Mailpit inbox (empty until the app sends an email).

### 4.1 Request Flow: Browser to Database and Back

When a user opens a page that needs data, here's what happens step by step:

**Example: User opens the Properties page**

```
Step 1:  Browser URL changes to /properties
Step 2:  React Router renders PropertiesPage component
Step 3:  PropertiesPage uses TanStack Query hook (useQuery)
Step 4:  TanStack Query calls Axios to fetch data
Step 5:  Axios sends GET http://localhost:8000/api/v1/properties
         (with Authorization: Bearer <token> header)
Step 6:  Laravel receives the request
Step 7:  Route matches → PropertyController@index
Step 8:  Controller calls PropertyService::listForOwner($ownerId)
Step 9:  Service runs: Property::where('owner_id', $ownerId)->get()
Step 10: Eloquent sends SQL to PostgreSQL:
         SELECT * FROM properties WHERE owner_id = 1
Step 11: PostgreSQL returns rows
Step 12: Eloquent converts rows to Property model objects
Step 13: Controller returns JSON response (HTTP 200)
Step 14: Axios receives the JSON
Step 15: TanStack Query stores the data in its cache
Step 16: React re-renders the page with the property list
```

**Diagram:**

```
Browser (you)
    │ URL: /properties
    ▼
React Router → PropertiesPage component
    │
    ▼
TanStack Query (useQuery)
    │ "I need data from /api/v1/properties"
    ▼
Axios (HTTP client)
    │ GET /api/v1/properties
    │ Authorization: Bearer abc123...
    ▼
Laravel Route (/api/v1/properties → PropertyController@index)
    │
    ▼
PropertyController
    │ calls PropertyService
    ▼
PropertyService
    │ Property::where('owner_id', $ownerId)->get()
    ▼
Eloquent ORM
    │ SELECT * FROM properties WHERE owner_id = 1
    ▼
PostgreSQL
    │ returns rows
    ▲
    │ (response travels back up the same path)
    │
Browser shows: list of properties
```

**Key insight:** The frontend never talks directly to the database. Every data request goes through the full chain: React → Axios → Laravel → Eloquent → PostgreSQL → back.

### 4.2 Frontend Routing Flow

React Router handles navigation without full page reloads. Here's how it works:

```
User clicks "Bookings" in sidebar
    │
    ▼
Browser URL changes to /bookings (no server request)
    │
    ▼
React Router checks route definitions (src/routes/index.tsx)
    │
    ├── Is /bookings a public route? No.
    ├── Is /bookings a protected route? Yes.
    │
    ▼
ProtectedLayout component runs
    │
    ├── Check: does localStorage have an auth token?
    │
    ├── YES → Render AppShell (sidebar + header) with BookingsPage inside
    │
    └── NO → Redirect to /login (Navigate component)
```

**Important points:**

- Changing routes does NOT make a backend request. Only the page component changes.
- Backend requests happen only when a page component needs data (via TanStack Query).
- `PublicLayout` wraps `/login` and `/register` — no sidebar, just centered content.
- `ProtectedLayout` wraps all other routes — includes the AppShell with sidebar navigation.
- The auth token check is instant (reads localStorage) — no API call needed just to navigate.

**Route structure:**

```
/login          → PublicLayout  → LoginPage
/register       → PublicLayout  → RegisterPage
/dashboard      → ProtectedLayout → AppShell → DashboardPage
/properties     → ProtectedLayout → AppShell → PropertiesPage
/bookings       → ProtectedLayout → AppShell → BookingsPage
... (all other protected routes)
```

### 4.3 API Client and Auth Token Flow

The file `frontend/src/lib/api.ts` creates a configured Axios instance. Here's how the auth flow works:

**Login flow (future, Task 2.10):**

```
1. User enters email + password on login page
2. Axios sends POST /api/v1/auth/login with credentials
3. Laravel validates credentials, creates Sanctum token
4. Laravel returns: { "token": "abc123...", "owner": { ... } }
5. Frontend stores token: localStorage.setItem('lodgeflow_token', 'abc123...')
6. Frontend redirects to /dashboard
```

**Subsequent request flow (every API call after login):**

```
1. Page component triggers API call via TanStack Query
2. TanStack Query calls Axios
3. Axios REQUEST INTERCEPTOR fires:
   - Reads token from localStorage
   - Adds header: Authorization: Bearer abc123...
4. Request goes to Laravel
5. Laravel Sanctum middleware reads the Bearer token
6. Sanctum identifies which Owner this token belongs to
7. Request proceeds with authenticated owner context
```

**401 Unauthorized flow (token expired or invalid):**

```
1. Axios sends request with token
2. Laravel returns HTTP 401 (token invalid/expired)
3. Axios RESPONSE INTERCEPTOR fires:
   - Detects status === 401
   - Clears token: localStorage.removeItem('lodgeflow_token')
   - Redirects browser to /login
4. User must log in again
```

**Why this matters:** You never manually add auth headers to API calls. The interceptor does it automatically for every request. And if the token expires, the user is automatically sent back to login.

### 4.4 Backend Request Handling Flow

When Laravel receives an API request, it goes through several layers:

```
HTTP Request arrives
    │
    ▼
Middleware (auth:sanctum)
    │ Verifies Bearer token, identifies Owner
    │ If invalid → returns 401 immediately
    ▼
Route matching (routes/api.php)
    │ Finds: POST /properties → PropertyController@store
    ▼
Form Request validation (StorePropertyRequest)
    │ Checks: name required, max 100 chars
    │         address required, max 255 chars
    │ If invalid → returns 422 with field errors
    ▼
Controller (PropertyController@store)
    │ Calls: $this->propertyService->create($validatedData)
    ▼
Service (PropertyService::create)
    │ Business logic:
    │ - Sets owner_id from authenticated user
    │ - Creates Property via Eloquent
    ▼
Eloquent Model (Property::create([...]))
    │ INSERT INTO properties (owner_id, name, address, ...) VALUES (...)
    ▼
PostgreSQL
    │ Stores the row, returns the new record
    ▲
    │
Controller returns JSON response (HTTP 201)
```

**Future example: POST /api/v1/properties**

```
Request body: { "name": "Sunrise Homestay", "address": "123 Jalan Bunga" }
Header: Authorization: Bearer abc123...

Step 1: Sanctum verifies token → Owner ID = 1
Step 2: Route matches → PropertyController@store
Step 3: StorePropertyRequest validates:
        ✓ name = "Sunrise Homestay" (present, ≤100 chars)
        ✓ address = "123 Jalan Bunga" (present, ≤255 chars)
Step 4: Controller calls PropertyService::create(data, ownerId=1)
Step 5: Service creates: Property::create([
            'owner_id' => 1,
            'name' => 'Sunrise Homestay',
            'address' => '123 Jalan Bunga',
            'is_active' => true
        ])
Step 6: PostgreSQL inserts row, returns ID = 7
Step 7: Controller returns HTTP 201:
        { "data": { "id": 7, "name": "Sunrise Homestay", ... } }
```

**What if validation fails?**

```
Request body: { "name": "", "address": "" }

Step 1: Sanctum verifies token → OK
Step 2: Route matches → PropertyController@store
Step 3: StorePropertyRequest validates:
        ✗ name is required
        ✗ address is required
Step 4: Laravel returns HTTP 422:
        {
          "message": "The name field is required. (and 1 more error)",
          "errors": {
            "name": ["The name field is required."],
            "address": ["The address field is required."]
          }
        }
```

The request never reaches the controller or service — validation stops it early.

### 4.5 Database Interaction Flow

**PostgreSQL is the source of truth.** All persistent data lives there. If a container restarts, the data survives (stored in a Docker volume).

**How Laravel talks to PostgreSQL:**

```
Laravel code:  Property::where('owner_id', 1)->where('is_active', true)->get()
                │
                ▼ (Eloquent translates to SQL)
SQL sent:      SELECT * FROM properties WHERE owner_id = 1 AND is_active = true
                │
                ▼
PostgreSQL:    Executes query, returns matching rows
                │
                ▼
Eloquent:      Converts each row into a Property model object
                │
                ▼
Your code:     Gets a Collection of Property objects with ->name, ->address, etc.
```

**Key concepts:**

- **Migrations** define database structure (tables, columns, indexes). They're PHP files in `backend/database/migrations/`. Running `php artisan migrate` executes them in order.
- **Models** represent database tables in PHP. `Property` model = `properties` table. Each model instance = one row.
- **Relationships** define how tables connect:
  - Owner hasMany Properties (one owner can have multiple properties)
  - Property belongsTo Owner (each property has one owner)
  - Property hasMany Units (one property can have multiple rooms)

**The frontend NEVER talks directly to PostgreSQL.** There's no database connection from the browser. All data access goes through the Laravel API.

### 4.6 Queue and Background Job Flow

Some operations should happen in the background so the user doesn't wait. Here's how the queue system works:

**Future example: Booking checkout creates a cleaning task**

```
Step 1:  Owner clicks "Check Out" on a booking
Step 2:  React sends PATCH /api/v1/bookings/42/check-out
Step 3:  Laravel updates booking status to "checked_out"
Step 4:  Laravel dispatches CreateCleaningTaskJob to Redis:
         CreateCleaningTaskJob::dispatch(
             bookingId: 42,
             unitId: 5,
             ownerId: 1
         )->onQueue('cleaning-tasks')
Step 5:  Laravel returns HTTP 200 to frontend immediately
         (user sees "Checkout successful" right away)
Step 6:  Redis stores the job in the "cleaning-tasks" queue
Step 7:  Queue worker (separate container) polls Redis
Step 8:  Queue worker picks up the job
Step 9:  Job creates CleaningTask in PostgreSQL:
         CleaningTask::create([
             'owner_id' => 1,
             'unit_id' => 5,
             'booking_id' => 42,
             'status' => 'pending'
         ])
Step 10: Done. Next time the owner views cleaning tasks, the new one appears.
```

**Diagram:**

```
Frontend                    Laravel API              Redis              Queue Worker
   │                            │                     │                     │
   │ PATCH /check-out           │                     │                     │
   │───────────────────────────▶│                     │                     │
   │                            │ update booking      │                     │
   │                            │ dispatch job ──────▶│                     │
   │◀─── 200 OK ───────────────│                     │                     │
   │                            │                     │                     │
   │ (user sees success)        │                     │ worker polls ◀──────│
   │                            │                     │ job found ─────────▶│
   │                            │                     │                     │
   │                            │                     │              create CleaningTask
   │                            │                     │              in PostgreSQL
```

**What if the job fails?**

```
Attempt 1: Job fails (e.g., database timeout)
           → Laravel logs the error
           → Waits 60 seconds

Attempt 2: Job fails again
           → Laravel logs the error
           → Waits 60 seconds

Attempt 3: Job fails again
           → Laravel logs PERMANENT FAILURE
           → Job moves to failed_jobs table
           → Manual investigation needed
```

**Why use a queue instead of doing it immediately?**

- The API responds faster (user doesn't wait for the cleaning task to be created)
- If the cleaning task creation fails, it doesn't break the checkout
- Failed jobs can be retried automatically
- Heavy operations don't slow down the API for other users

### 4.7 Docker Runtime Interaction

All Docker Compose services run on the same internal Docker network. They communicate using service names as hostnames.

**Inside Docker (container-to-container):**

```
api container → connects to "db" on port 5432      (PostgreSQL)
api container → connects to "redis" on port 6379   (Redis)
api container → connects to "mailpit" on port 1025 (SMTP)
queue-worker  → connects to "db" on port 5432      (PostgreSQL)
queue-worker  → connects to "redis" on port 6379   (Redis)
frontend      → connects to "api" on port 8000     (API proxy)
```

**From your Windows browser (outside Docker):**

```
Browser → localhost:5173  → mapped to frontend container port 5173
Browser → localhost:8000  → mapped to api container port 8000
Browser → localhost:8025  → mapped to mailpit container port 8025
```

**Why `DB_HOST=db` works inside Docker:**

Docker Compose creates a network where each service's name becomes a DNS hostname. The `api` container can resolve `db` to the PostgreSQL container's IP address. This is like how `google.com` resolves to an IP address on the internet, but within the Docker network.

**Why `DB_HOST=127.0.0.1` is needed in GitHub Actions:**

In CI, there's no Docker Compose network. Service containers (PostgreSQL, Redis) are exposed on the runner's localhost. So the test runner connects to `127.0.0.1:5432` instead of `db:5432`.

### 4.8 Local Development Flow When Editing Code

**Volume mounts** make your local files appear inside containers:

```
Your laptop:  C:\...\lodgeflow\backend\   ←→  api container: /app/
Your laptop:  C:\...\lodgeflow\frontend\  ←→  frontend container: /app/
```

**When you edit a Laravel file:**
1. You save `backend/app/Modules/Property/Services/PropertyService.php`
2. The file is instantly visible inside the `api` container (volume mount)
3. Next API request uses the updated code (PHP reloads on each request in dev)

**When you edit a React file:**
1. You save `frontend/src/features/properties/PropertiesPage.tsx`
2. The file is instantly visible inside the `frontend` container (volume mount)
3. Vite detects the change and hot-reloads the browser (page updates without refresh)

**What about dependencies?**

- `vendor/` (PHP packages) — generated by `composer install`, lives in a Docker volume, NOT committed to Git
- `node_modules/` (JS packages) — generated by `npm install`, lives in a Docker volume, NOT committed to Git
- `package-lock.json` and `composer.lock` — committed to Git (ensures everyone gets the same dependency versions)

**Why dependencies aren't committed:**
- `vendor/` can be 50-200 MB
- `node_modules/` can be 200-500 MB
- They're generated from `composer.lock` / `package-lock.json` — reproducible
- Different operating systems may need different binary builds

### 4.9 CI Interaction Flow

Here's what happens after you push a branch and open a PR:

```
You: git push origin feature/12-property-crud
     │
     ▼
GitHub: receives the branch
     │
     ▼
GitHub: PR opened (or push to existing PR)
     │
     ▼
GitHub Actions: triggered by PR event
     │
     ├── Backend Job (runs in parallel)
     │   │
     │   ▼ Fresh Ubuntu runner (clean machine, nothing installed)
     │   │
     │   ▼ Start PostgreSQL 16 container (accessible at 127.0.0.1:5432)
     │   ▼ Start Redis 7 container (accessible at 127.0.0.1:6379)
     │   │
     │   ▼ Install PHP 8.3 + extensions
     │   ▼ composer install (downloads all PHP packages)
     │   ▼ Copy .env.testing → .env
     │   ▼ php artisan migrate (creates tables in test database)
     │   ▼ php artisan test (runs all PHPUnit/Pest tests)
     │   │
     │   └── Result: ✓ PASS or ✗ FAIL
     │
     ├── Frontend Job (runs in parallel)
     │   │
     │   ▼ Fresh Ubuntu runner
     │   │
     │   ▼ Install Node 20
     │   ▼ npm ci (installs exact versions from package-lock.json)
     │   ▼ npm run build (TypeScript compile + Vite bundle)
     │   │
     │   └── Result: ✓ PASS or ✗ FAIL
     │
     ▼
GitHub: Both jobs passed?
     │
     ├── YES → Green checkmark, PR can be merged
     └── NO  → Red X, PR is blocked from merging
```

**Key points:**
- Each CI run starts from scratch — nothing is cached between runs (except Composer/npm caches for speed)
- CI uses `127.0.0.1` for database because there's no Docker Compose network
- CI provides `APP_KEY` as an environment variable (not generated dynamically)
- Both jobs run in parallel — total CI time is the slower of the two, not the sum

### 4.10 Common Confusion Points

**"localhost" means different things depending on where you are:**

| Context | What localhost means |
|---------|---------------------|
| Your Windows browser | Your laptop (connects to Docker port mappings) |
| Inside the `api` container | The api container itself (not your laptop) |
| Inside GitHub Actions runner | The CI runner machine |

That's why:
- Your browser uses `localhost:8000` to reach the API
- The `api` container uses `db` (not `localhost`) to reach PostgreSQL
- CI uses `127.0.0.1` to reach PostgreSQL (it's on the same runner)

---

**Why Docker uses service names like `db` and `redis`:**

Docker Compose creates a private network. Each service gets a DNS name matching its service name in `docker-compose.yml`. The `api` service can reach PostgreSQL by connecting to hostname `db` — Docker resolves this to the correct container IP.

---

**Why the frontend doesn't connect directly to PostgreSQL:**

- Browsers can't make PostgreSQL connections (it's not HTTP)
- Exposing the database to the browser would be a massive security risk
- Business logic (validation, authorization) must run on the server
- The API is the gatekeeper — it decides what data the frontend can see

---

**Why queue-worker uses the same code as api but a different command:**

Both containers use the same Docker image (same PHP code, same Laravel app). The difference is what command they run:
- `api` runs: `php artisan serve` (listens for HTTP requests)
- `queue-worker` runs: `php artisan queue:work` (listens for Redis jobs)

Same code, different entry point. Like the same restaurant kitchen that can serve dine-in customers (api) or process delivery orders (queue-worker).

---

**Why vendor/ and node_modules/ are not committed:**

- They're huge (hundreds of MB)
- They're generated from lock files (`composer.lock`, `package-lock.json`)
- Different operating systems may need different binary builds
- Running `composer install` or `npm ci` recreates them identically from the lock files

---

**Difference between `docker compose run` and `docker compose exec`:**

| Command | Creates new container? | Requires service to be running? |
|---------|----------------------|-------------------------------|
| `docker compose run --rm api ...` | Yes (temporary) | No (starts dependencies) |
| `docker compose exec api ...` | No (uses existing) | Yes (must already be running) |

Use `run` for one-off commands (migrations, tests). Use `exec` to interact with an already-running container.

---

**Difference between application code, dependencies, containers, and images:**

| Concept | Example | Committed to Git? | Where it lives |
|---------|---------|-------------------|----------------|
| Application code | `PropertyService.php`, `App.tsx` | Yes | Your laptop + GitHub |
| Dependencies | `vendor/`, `node_modules/` | No | Docker volumes |
| Lock files | `composer.lock`, `package-lock.json` | Yes | Your laptop + GitHub |
| Docker images | `lodgeflow-api:latest` | No | Docker's local cache |
| Containers | `lodgeflow-api-1` | No | Running in Docker |
| Dockerfiles | `docker/backend/Dockerfile` | Yes | Your laptop + GitHub |

### 4.11 One Complete Future Example

Here's a full end-to-end workflow showing every component involved:

**Scenario: Owner creates a booking, then checks out the guest**

---

**Part A: Owner creates a booking**

```
Step 1:  Owner navigates to /bookings in the browser
Step 2:  React Router renders BookingsPage inside ProtectedLayout
```

## 5. Laravel Backend Setup Explained

### What Laravel does in this project

Laravel is a PHP framework. In LodgeFlow, it serves as the **API backend only**. It:
- Receives HTTP requests from the React frontend
- Validates input data
- Enforces business rules
- Reads/writes data in PostgreSQL
- Returns JSON responses
- Dispatches background jobs to Redis

### Why API-only (no Blade)?

Laravel can render HTML pages using its "Blade" template engine. We chose NOT to use Blade because:
- A separate React frontend gives a better user experience (faster navigation, no full page reloads)
- Frontend and backend can be developed independently
- The API can be reused later (mobile app, third-party integrations)
- MYDS (Malaysia Government Design System) provides React components, not Blade components

### Why PostgreSQL instead of SQLite?

SQLite is a file-based database — simple but limited. PostgreSQL is a full database server that supports:
- CHECK constraints (e.g., "check_out_date must be after check_in_date")
- Proper DECIMAL types for financial calculations (no floating-point errors)
- Concurrent access (multiple users/processes reading/writing simultaneously)
- Date range operations needed for booking overlap detection

For a production-ready app handling money, PostgreSQL is the right choice.

### Why Redis for queue/cache?

Redis is an in-memory data store — extremely fast. We use it for:
- **Queue:** When the owner checks out a guest, the API queues a "create cleaning task" job in Redis. The queue worker picks it up and processes it. This keeps the API response fast.
- **Cache:** Dashboard calculations (monthly income, expenses) can be cached in Redis so they don't hit the database on every page load.

### Why Mailpit?

During development, you don't want to send real emails. Mailpit catches all outgoing emails so you can:
- Verify email content looks correct
- Test password reset flows
- Debug email-related issues

### What `app/Modules/` means

Instead of putting all code in Laravel's default folders (`app/Http/Controllers/`, `app/Models/`), we organise code by business domain:

```
app/Modules/
├── Property/       ← everything about properties
├── Booking/        ← everything about bookings
├── Payment/        ← everything about payments
└── ...
```

Each module contains its own controllers, services, models, policies, and routes. This keeps related code together and makes it easy to find things.

### What "modular monolith" means

- **Monolith:** The entire backend is one application, deployed as one unit. There's one database, one codebase, one Docker image.
- **Modular:** The code inside is organised into separate modules with clear boundaries.

This is simpler than microservices (where each module would be a separate application with its own database and deployment). For a learning project with one developer, a modular monolith gives you the organisational benefits without the operational complexity.

### Why no Repository classes?

The "Repository pattern" adds an extra layer between your service code and the database. For simple CRUD operations, this is unnecessary boilerplate. Our services query Eloquent (Laravel's ORM) directly:

```php
// Simple and direct — no repository needed
$properties = Property::where('owner_id', $ownerId)->get();
```

If queries become complex or need reuse across multiple services, we can add repositories later.

## 6. React Frontend Setup Explained

### What React does

React is a JavaScript library for building user interfaces. It lets you create reusable components (buttons, forms, cards) and compose them into pages. When data changes, React efficiently updates only the parts of the page that need to change.

### What Vite does

Vite is a build tool and development server. During development, it serves your React code with instant hot-reload (you save a file, the browser updates immediately). For production, it bundles everything into optimised static files.

### What TypeScript does

TypeScript adds type checking to JavaScript. Instead of discovering bugs at runtime ("Cannot read property 'name' of undefined"), TypeScript catches them at compile time:

```typescript
// TypeScript catches this mistake before you run the code
const booking: Booking = { checkIn: '2024-01-01' }
console.log(booking.checkOut.length) // Error: 'checkOut' might be undefined
```

We enabled "strict mode" which is the most thorough level of type checking.

### What MYDS is used for

MYDS (Malaysia Government Design System) provides pre-built React components styled according to Malaysian government digital standards. We use it for:
- Buttons, form inputs, dropdowns
- Typography and spacing
- Alerts and notifications
- Navigation components

This gives the app a professional, consistent look without custom design work.

### What TanStack Query will be used for

TanStack Query (formerly React Query) manages "server state" — data that comes from the API. It handles:
- Fetching data from the API
- Caching responses (so you don't re-fetch on every page navigation)
- Background refetching (keeping data fresh)
- Loading and error states

We installed it in v0.1.0 but will use it heavily starting in v0.2.0 when we build real screens.

### What Axios does

Axios is an HTTP client library. It sends requests to the Laravel API and receives responses. Our configured instance (`frontend/src/lib/api.ts`) automatically:
- Adds the auth token to every request
- Redirects to the login page if the API returns 401 (unauthorized)

### What React Router does

React Router handles navigation in the single-page app. When you click "Properties" in the sidebar, React Router shows the Properties page without a full page reload. It also:
- Defines which URLs map to which pages
- Supports protected routes (redirect to login if not authenticated)
- Supports nested layouts (sidebar + content area)

### What ProtectedLayout means

`ProtectedLayout` is a wrapper component that checks if the user has an auth token in localStorage. If yes, it renders the app shell (sidebar + content). If no, it redirects to `/login`. This prevents unauthenticated users from seeing protected pages.

### Why frontend and backend are separate

Keeping them separate means:
- The frontend team (or you working on UI) can work without touching PHP
- The backend team (or you working on API) can work without touching React
- The API can serve multiple clients (web, mobile, third-party) in the future
- Each can be deployed independently if needed later

## 7. Git and GitHub Workflow Explained

### What is a commit?

A commit is a snapshot of your code at a point in time. It records what changed, who changed it, and when. You can always go back to any previous commit.

```bash
git commit -m "feat: add property CRUD API"
```

### What is a branch?

A branch is a parallel version of your code. You create a branch to work on a feature without affecting `main`. When the feature is done and tested, you merge it back.

```
main:     A ─── B ─── C ─── D ─── E (stable, tested code)
                       │           ▲
feature:               └── X ── Y ─┘ (your work, merged via PR)
```

### What is main?

`main` is the primary branch — the "source of truth." It should always contain working, tested code. You never push directly to `main`; you always go through a pull request.

### What is a pull request (PR)?

A PR is a request to merge your branch into `main`. It:
- Shows exactly what changed (diff view)
- Triggers CI to run tests automatically
- Allows review before merging
- Creates a record of why changes were made

### Why branch protection?

Branch protection prevents anyone (including you) from pushing directly to `main`. Every change must:
1. Be on a separate branch
2. Pass CI (backend tests + frontend build)
3. Be merged via a PR

This ensures `main` is always in a working state.

### Why CI must pass before merge?

Without CI, you might accidentally merge broken code. CI automatically runs tests and builds on every PR. If something fails, you can't merge until you fix it. This is your safety net.

### Why not push directly to main?

Pushing directly to `main` means:
- No tests run before the code lands
- No review opportunity
- If something breaks, it's already in `main` and affects everyone
- No clear record of what changed and why

The PR workflow adds a small amount of friction but prevents much larger problems.

## 8. GitHub Actions CI Explained

### What CI means

CI stands for "Continuous Integration." It means automatically testing code every time someone proposes a change. In our case, GitHub Actions runs two jobs on every PR:

1. **Backend Tests** — installs PHP, sets up PostgreSQL + Redis, runs Laravel migrations, runs `php artisan test`
2. **Frontend Build** — installs Node, runs `npm ci`, runs `npm run build` (which includes TypeScript compilation)

If either job fails, the PR is blocked from merging.

### What the backend job checks

- Can Composer install all PHP dependencies without errors?
- Can Laravel connect to PostgreSQL and run migrations?
- Do all PHP tests pass?

### What the frontend job checks

- Can npm install all JavaScript dependencies without errors?
- Does TypeScript compile without type errors?
- Does Vite build the production bundle without errors?

### Why CI caught the missing APP_KEY

Laravel encrypts cookies and sessions using an `APP_KEY`. Without it, many Laravel commands fail. In Docker, we generate the key during setup. In CI, we initially forgot to provide one. The fix was adding `APP_KEY: base64:AAA...` to the CI environment variables.

**Lesson:** CI runs in a fresh environment every time — nothing is carried over from previous runs. You must explicitly provide everything the app needs.

### Why DB_HOST differs between Docker and CI

In Docker Compose, services communicate using their service names as hostnames:
- The `api` container connects to PostgreSQL using `DB_HOST=db` (the service name)

In GitHub Actions, service containers are accessible on `localhost`:
- The test runner connects to PostgreSQL using `DB_HOST=127.0.0.1`

This is why we set `DB_HOST` in the CI workflow's `env` block — it overrides the value in `.env.testing`.

### Why Node 20 action warnings are not blocking

GitHub Actions may show deprecation warnings about Node.js 16/20 in some actions. These are informational — they don't cause failures. The actions still work correctly. They'll be resolved when action maintainers release updates.

## 9. Problems Encountered and Fixes (Detailed)

### Problem: Git push failed before first commit

**What happened:** Running `git push` on a brand new repository with no commits gave an error.

**Why:** Git can't push "nothing." You need at least one commit before pushing.

**How we fixed it:** Created `.gitignore`, staged it with `git add .gitignore`, committed with `git commit -m "chore: initial commit"`, then pushed.

**Lesson:** Always make an initial commit before trying to push to a remote.

---

### Problem: Docker CLI available but Docker engine not running

**What happened:** `docker --version` worked (showed Docker 29.1.3) but `docker compose up` failed with "cannot find file."

**Why:** The Docker CLI is just a command-line tool. It needs the Docker Engine (daemon) running in the background. Docker Desktop must be started first.

**How we diagnosed it:** `docker info` showed an error about connecting to the daemon.

**How we fixed it:** Started Docker Desktop, waited for it to initialise, then retried.

**Lesson:** Docker CLI ≠ Docker Engine. Always ensure Docker Desktop is running before using Docker commands.

---

### Problem: Laravel scaffold created SQLite database

**What happened:** The Laravel installer created `backend/database/database.sqlite` and configured SQLite as the default database.

**Why:** Laravel's default installer uses SQLite for simplicity. LodgeFlow needs PostgreSQL for its features (CHECK constraints, DECIMAL precision, concurrent access).

**How we fixed it:**
1. Changed `config/database.php` default from `'sqlite'` to `'pgsql'`
2. Deleted `database/database.sqlite`
3. Added `database/database.sqlite` to `.gitignore`
4. Configured `.env.example` with PostgreSQL connection details

**Lesson:** Framework defaults are for quick demos. Production apps need explicit configuration for their chosen database.

---

### Problem: vendor/autoload.php missing

**What happened:** Running `php artisan` commands in the container failed with "Cannot open file vendor/autoload.php."

**Why:** The `vendor/` directory contains all PHP dependencies installed by Composer. It's not committed to Git (it's in `.gitignore`). After cloning or scaffolding, you must run `composer install` to create it.

**How we fixed it:** Ran `docker compose run --rm api composer install` inside the container.

**Lesson:** After cloning a PHP project, always run `composer install` before anything else. Same for Node projects with `npm install`.

---

### Problem: GitHub Actions backend failed — missing APP_KEY

**What happened:** The CI backend job failed with a Laravel error about missing encryption key.

**Why:** Laravel requires `APP_KEY` for encryption. In local development, we generate it with `php artisan key:generate`. In CI, the `.env` file is copied from `.env.testing` which had a key, but the CI environment variables (which take precedence) didn't include one.

**How we diagnosed it:** Read the CI job logs — the error message clearly said "No application encryption key has been specified."

**How we fixed it:** Added `APP_KEY: base64:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=` to the backend job's `env` section. This is a dummy key safe for testing (never use it in production).

**Lesson:** CI environments start completely fresh. Every required configuration must be explicitly provided — nothing is "remembered" from previous runs.

---

### Problem: PowerShell curl alias

**What happened:** Running `curl http://localhost:8000/api/v1/health` in PowerShell returned an HTML object instead of the JSON response.

**Why:** PowerShell aliases `curl` to `Invoke-WebRequest`, which returns a PowerShell object, not raw text. The real `curl` executable is `curl.exe` on Windows.

**How we fixed it:** Used `curl.exe -s http://localhost:8000/api/v1/health` instead.

**Lesson:** On Windows PowerShell, always use `curl.exe` (with the `.exe` extension) to get the real curl behaviour. Alternatively, use `Invoke-RestMethod` for a PowerShell-native approach.

---

### Problem: npm create vite interactive prompts blocked in Docker

**What happened:** Running `npm create vite@latest` inside a Docker container hung indefinitely, waiting for interactive input.

**Why:** The command has interactive prompts ("Ok to proceed?", "Directory not empty, what to do?"). Docker containers don't have an interactive terminal by default.

**How we fixed it:** Instead of fighting the interactive tool, we created all frontend files manually (package.json, tsconfig.json, vite.config.ts, etc.). This is actually more reliable and gives us full control.

**Lesson:** Interactive CLI tools don't work well in non-interactive environments (Docker, CI). When scaffolding tools are problematic, creating files manually is a valid approach.

---

### Problem: MYDS package version not found on npm

**What happened:** `npm install` failed with "No matching version found for @govtechmy/myds-react@^0.1.0."

**Why:** We guessed the version range. The actual published versions started at `0.0.1` and the latest was `1.0.2`.

**How we diagnosed it:** Ran `npm view @govtechmy/myds-react versions --json` to see all published versions.

**How we fixed it:** Changed the version in `package.json` from `^0.1.0` to `^1.0.0`.

**Lesson:** Always check the actual published versions of a package before adding it to `package.json`. Use `npm view <package> versions` to see what's available.

---

### Problem: MYDS CSS import path was wrong

**What happened:** `npm run build` failed with "Missing ./css/global.css specifier in @govtechmy/myds-style package."

**Why:** We guessed the import path. The package doesn't export `./css/global.css` — it exports `./full.css`.

**How we diagnosed it:** Read the package's `package.json` (inside `node_modules/@govtechmy/myds-style/package.json`) to see the `exports` field.

**How we fixed it:** Changed the import in `main.tsx` from `@govtechmy/myds-style/css/global.css` to `@govtechmy/myds-style/full.css`.

**Lesson:** When an import fails, check the package's `package.json` `exports` field to see what paths are actually available.

---

### Problem: Local Docker and GitHub Actions need different DB_HOST values

**What happened:** Backend tests passed locally in Docker but failed in GitHub Actions CI with a "could not connect to server" database error. Conversely, hardcoding `DB_HOST=127.0.0.1` would break local Docker tests.

**Why:** Docker Compose creates a private network where services are reachable by their service name. The `api` container connects to PostgreSQL using hostname `db` (the service name in `docker-compose.yml`). In GitHub Actions, there is no Docker Compose network — PostgreSQL runs as a service container exposed on the runner's localhost (`127.0.0.1`).

**How we diagnosed it:** The CI error log showed "could not translate host name 'db' to address." This made it clear that `db` is not a valid hostname in the CI environment.

**How we fixed it:** We keep `DB_HOST=db` in the local Docker configuration (`.env.testing`) and override it with `DB_HOST=127.0.0.1` in the GitHub Actions workflow file (`.github/workflows/ci.yml`) using job-level environment variables. Laravel reads environment variables with higher priority than `.env` files, so the CI override wins.

**Lesson:** Do not force one database host value to fit every environment. Let each environment provide its own values. Local Docker uses service names; CI uses localhost. The application code stays the same — only the environment configuration differs.
